Signing keys

A signing key is what proves an update came from the same person as the original. Android will not accept an app without one, and it will not accept an update signed by a different one.

Read this before you make one

If you lose your signing key, you cannot update your app. Not "it is difficult" - you cannot. Google will not reset it and there is no appeal. Your only option is publishing a new listing under a new package name, starting from zero installs and zero reviews, and asking everybody to install the new one.

Back it up somewhere that is not your laptop, on the day you make it.

Making one

A key lives in a keystore file. If you have Java installed, this makes one: 

keytool -genkey -v \
  -keystore my-app.jks \
  -alias my-app \
  -keyalg RSA -keysize 2048 \
  -validity 10000

It asks for a password and a few details about you. Twenty-seven years of validity sounds absurd; it is the normal recommendation, because an expired key has the same consequence as a lost one.

Keep three things together, and safe:

  • The .jks file
  • The keystore password
  • The key alias and its password

Uploading it

On the Signing page, upload the keystore and enter the alias. That is all that gets stored.

Passwords are not stored here

You type them each time you build. They are used to write a temporary file that the Android build reads, and that file is deleted as soon as the build finishes. Passwords are never written into your project settings, never included in any download, and never logged.

The keystore file itself is stored, because the build needs it. Without a password it cannot be used.

What gets signed

Both the APK and the AAB, with the same key. An app signed with a development key installs on a phone but Google Play will refuse it, which is a slow way to discover the problem - the upload fails after both the build and the upload have been waited through.

If Web2App cannot recognise the Android build file well enough to add your signing configuration, it stops the build and says so. Quietly producing a debug-signed file that looks like a release is the worst available outcome, so it is not one of the options.

Play App Signing

Google Play offers to hold a second key and re-sign your app itself. If you opt in, the key you make here becomes your upload key - the one that proves an upload is from you - and Google holds the key that phones actually verify.

It is worth taking. An upload key can be reset by Google if you lose it; the app signing key cannot. It turns the worst case from "start again from zero" into a support request.

iPhone signing

Different mechanism entirely, and it does not happen here. Apple signing is handled in Xcode on a Mac with your Apple Developer account, and the project .zip carries no signing configuration at all - see Publishing.

Backing it up

Somewhere that survives losing your computer:

  • A password manager - most will store a file alongside the passwords.
  • An encrypted archive in cloud storage.
  • A printed copy of the passwords somewhere physically safe.

Not in your git repository, and not in an email to yourself. The file plus the password is complete control of your app's identity.

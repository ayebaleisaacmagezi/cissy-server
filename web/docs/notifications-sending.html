Sending

Two ways, and you can use both. Type a message by hand in Firebase, or have your own server send when something happens.

By hand, from the Firebase Console

Nothing to build. In your Firebase project, open Messaging, compose a notification, choose your app, and send. Good for announcements, news, an offer this weekend.

Under Additional options you can add custom data, which is how you make the notification open a particular page:

KeyValue
actionopen_url
url/offers/weekend

Leave those out and tapping the notification just opens the app.

From your own server

This is the one that matters, because it is the only way to send when something actually happens - an order is ready, a result is published, a message arrives.

Get a service-account key

In Firebase: Project settings → Service accounts → Generate new private key. You get a JSON file.

That file is a password for your project

Anyone holding it can send notifications to all your users. Keep it on your server, out of your git repository, and never in anything a browser downloads. Do not send it to us - we have no use for it and no way to keep it safer than you can.

The usual arrangement is to store it outside the web root and point the GOOGLE_APPLICATION_CREDENTIALS environment variable at it.

Code for your stack

The Notifications page in the app generates this for Node.js, PHP, Laravel, Python, .NET, WordPress and plain HTTP, with your project ID and your category names already filled in. Pick your backend there and copy it. Here is the shape, using Node: 

// GOOGLE_APPLICATION_CREDENTIALS points at your service-account JSON.
const admin = require("firebase-admin");

admin.initializeApp({
  credential: admin.credential.applicationDefault(),
  projectId: "your-project-id",
});

await admin.messaging().send({
  topic: "orders",
  notification: {
    title: "Order ready",
    body: "Order #123 is ready for pickup.",
  },
  data: {
    action: "open_url",
    url: "/orders/123",
  },
});

The payload

Two parts, and the difference matters.

  • notification - the title and body the person reads. The phone displays these itself.
  • data - instructions for the app. The app reads action and url.
actionWhat happens on tap
open_urlOpens url in the app. A path is resolved against your website address.
noneOpens the app, nothing more.
The app checks the destination

Anything outside your allowed domains is ignored, and an action the app does not recognise does nothing. A notification arrives from the network, so it is treated as untrusted - it can open a page of yours and that is all it can do.

Sending to one person

Categories are broadcasts. To reach one person your backend has to know which device belongs to which user, and there are two ways to get that.

From your website, once they are signed in

Your pages can ask the app for the device's token. Your site already knows who is logged in, so it can send the token to your backend over its own session - no new endpoint and no new authentication to design. 

if (window.flutter_inappwebview) {
  const result = await window.flutter_inappwebview
    .callHandler('CissyBridge', { action: 'getPushToken' });

  if (result.status === 'ok') {
    await fetch('/api/my-devices', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ token: result.token }),
    });
  }
}

Store the token against the user. To send to them, use token: instead of topic:.

The bridge only answers on your allowed domains, so another site loaded in the app cannot call it. It also offers { action: 'getPlatform' } and { action: 'requestNotificationPermission' }.

Or have the app post it for you

If your site cannot run that JavaScript, set a push token endpoint on the Notifications page. The app posts to it whenever it gets or refreshes a token: 

POST https://yoursite.example/api/push-token
Content-Type: application/json

{ "token": "…", "platform": "android", "appVersion": "1.2.0" }

Your endpoint has to work out who this is - from a session cookie the app carries, or by having the person sign in first. That is why the JavaScript route above is usually simpler.

Tokens change

A device token is not permanent. It changes when the app is reinstalled, when data is cleared, and occasionally on its own. Always store the newest one you were given, and drop tokens that Firebase reports as unregistered when you send - otherwise your list fills up with dead entries.

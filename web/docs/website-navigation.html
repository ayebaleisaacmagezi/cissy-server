Hiding your site's navigation

If the app draws a native bottom bar and your website draws its own, the phone shows two. This is how you take one of them down.

Why it happens

The app renders your website exactly as a mobile browser would, including the navigation bar your site draws at the bottom of its own pages. The native bar is drawn by the app, outside the page, underneath it. Neither one knows the other exists.

The result costs more than screen space:

  • About a fifth of the screen, permanently. A bottom bar is roughly 56 points. Two of them is 110 to 120 out of a phone's 640 or so of usable height, gone on every page.
  • The same destinations twice. Home and Shop in both bars is four ways to reach two places, stacked.
  • They disagree. Your site highlights based on the page it is showing; the native bar highlights based on the tab last tapped. After an in-page link they say different things.
  • They behave differently. Your site's Shop navigates inside the page the user is on. The native Shop switches to a different tab. Two identical looking controls, one above the other, doing different things - that is the part that reads as broken rather than crowded.
None of this applies if you are not using native navigation

An app that uses your website's own navigation has one bar and is fine as it is. This page is only for apps with a native bottom bar.

Three ways, in the Studio

Open Studio and find the Website navigation card. You can use any of these, or more than one.

1. Hide elements by CSS selector

Write the selector the way you would in a stylesheet, and the app hides what it matches: 

.mobile-bottom-nav
#site-header .menu
footer.nav

Selectors only - no braces, no rule body. The app writes the rule for you. The preview in Studio shows the result on your real site immediately, so you can tell straight away whether you have pointed at the right thing.

Works on any site, including one you cannot edit. Breaks silently if the site is redesigned - if a class name changes, the selector stops matching and the bar comes back. Check after a redesign.

2. Add a class to the page

The app adds a class to <body>, and you write the rule in your own stylesheet: 

/* in your site's CSS */
body.web2app-native .site-bottom-nav {
  display: none;
}

In a normal browser nothing changes. Inside the app the class is there and your rule applies. This is the best option if you control your site's CSS: the rule lives next to the thing it hides, so a redesign that renames the bar renames it in both places at once.

It also lets you do more than hide. You can widen a container, remove bottom padding that existed to clear the bar, or show something only app users see.

3. A flag on the entry URL

The app can add something like source=web2app to the address it opens, so your server can render a different layout from the start.

This one is weaker than it looks

The flag is on the first address only. As soon as somebody taps a link inside your site it is gone, because rewriting every link would break your site's own routing. Treat it as a hint about how a visit started, not as a reliable signal. If you want something that lasts the whole session, set a cookie from your server the first time you see the flag.

Which to choose

MethodGood atWeak at
CSS selector Works anywhere, no site changes, instant. Breaks quietly when the site is redesigned.
Body class Survives redesigns; can do more than hide. You need to be able to edit your site's CSS.
URL flag Your server decides; can change the whole page. Only reaches the first page of a visit.

Where it applies

Only on your allowed domains. If somebody follows a link to another site and it opens inside the app, none of this touches that page - the app does not restyle pages that are not yours.

The hiding is applied before the page draws, so your bar does not appear and then vanish. It is re-applied when a page changes without a full reload, so single-page sites stay covered too.

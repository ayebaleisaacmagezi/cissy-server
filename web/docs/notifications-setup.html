Setting it up

Creating your Firebase project and connecting it to your app. Twenty minutes for Android, once.

Settle your identifiers first

Firebase registers an app against its package name, and so do Google Play and the App Store. Changing yours afterwards means redoing this and starting a new store listing. Check the Identity page before you begin.

  1. Turn push on Open the Notifications page for your app and switch it on. The page then walks you through the rest and tracks what is still outstanding.
  2. Create a Firebase project Open console.firebase.google.com, sign in with your own Google account, and create a project. Name it after your business. You can decline Google Analytics; notifications do not need it.
  3. Add an Android app to the project In the project, choose Add app and pick Android. It asks for a package name - paste the one shown on the Notifications page. It must match exactly. The nickname and the signing certificate fields can be left alone for now.
  4. Download google-services.json and upload it Firebase offers the file at the end of registration. Upload it on the Notifications page. Web2App reads it and checks it belongs to this app.
    If it says the file belongs to another app

    The file was downloaded from a different Firebase app. Go back to Firebase, add an app with the exact package name shown, and download that one's file. Uploading the wrong file would produce an app that builds, installs, and never receives anything - so it is refused.

  5. Set up your categories Add the categories you will send to - General, Offers, Order updates. Decide which are on by default for a new install. Marketing off by default is usually the right call; order updates on.
  6. Write the permission message This is your app's own explanation, shown before the phone's prompt. Say what people get, not that you would like permission. "Get told when your order is ready" beats "Enable notifications".
  7. Build and test Build the app, install it, and open it. On the second visit the app puts your explanation up and then asks the phone for permission. Then use the test panel at the foot of the Notifications page to send yourself one.

When the app asks

Not on first launch. Somebody who has just opened your app for the first time has no reason to say yes, and on both Android and iPhone a refusal can only be undone by the user digging into system settings. So the app waits until the second visit, shows your explanation first, and only asks the operating system if they agree to that.

That costs you a few days of delay and buys a much higher acceptance rate.

While the app is open

Both platforms hand a message to the app rather than displaying it when the app is in the foreground, so you choose what happens:

SettingWhat people see
Show a notificationThe same banner as when the app is closed. Predictable, and the default.
Show a bar in the appA quieter strip at the top with an Open button. Good for anything that arrives often.
Nothing visibleRecorded but not shown. For silent updates.

The notifications screen

You can give the app a tab that lists what this phone has received, with the category switches behind it. Add a navigation tab in Studio and set it to Notifications.

It is a convenience history kept on the phone, not a message store. It holds the last fifty, and clearing the app's data clears it. Anything that has to survive belongs on your own server.

Checking it worked

The foot of the Notifications page reports what is in place: whether the configuration is valid, whether the build you last made included push, and whether a device has registered. It also gives you a test device token you can paste into Firebase's own message composer.

If the test does not arrive
  • Was the app built after you uploaded the configuration file? Push is compiled in.
  • Did you accept the permission prompt on the phone?
  • Is the phone's notification setting for the app switched on in system settings?
  • If you sent to a category, is that category switched on inside the app?

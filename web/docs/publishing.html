Publishing

Getting the app into Google Play, and building the iPhone version on a Mac.

Google Play

  1. Create a Play developer account A one-off fee, paid to Google, in your own name. Identity verification takes a few days, so start it before you are ready to ship.
  2. Build an AAB Google Play does not accept APKs for new apps. Choose AAB on the Build page.
  3. Create the app in the Play Console Use the same package name as your Identity page. This cannot be changed afterwards.
  4. Fill in the store listing Title, short and full description, screenshots, a feature graphic, a privacy policy URL, and the content rating questionnaire. This is usually the slowest part, and none of it is technical.
  5. Upload the AAB and roll out Start with internal testing to check it installs and runs from the store, then promote it to production.
Two things that get web-wrapper apps rejected

Google's policy is against apps that are only a website with no added value. An app that offers native navigation, notifications, offline handling, downloads and sharing is not that - but it helps to say so in the listing, and to have those features actually switched on.

The other is permissions you do not use. If Camera or Location are on but your site never uses them, turn them off before you publish.

Updating

Remember that content changes need no release at all. Your app loads your live site, so publishing a page is publishing it to every installed app.

You only need a new build and a new upload when the app itself changes - the icon, navigation, modules, name, or a notification setting. Build, check the version code went up, upload, roll out.

iPhone

Apple's build tools only run on macOS, so the iPhone app cannot be built here. What you get instead is the complete Flutter project as a .zip, ready to open on a Mac.

  1. Download the project zip From the Build page. It is a couple of megabytes.
  2. Open it on a Mac with Xcode and Flutter installed Run flutter pub get in the project folder, then open the ios folder in Xcode.
  3. Set your signing team Select the Runner target, then Signing & Capabilities. Xcode handles certificates and provisioning from there.
  4. Add Push Notifications Only if you are using notifications. Same screen, press + Capability. See iPhone and APNs.
  5. Archive and upload to App Store Connect Product → Archive, then Distribute App. From there it is Apple's review process, which takes anywhere from a day to a week.
The zip carries no signing configuration

No certificates, no provisioning profiles, no keystore and no passwords. Apple signing belongs to your developer account on your Mac, and putting any of it in a downloadable file would be a mistake.

Do not have a Mac?

The project is a standard Flutter project, so anything that builds Flutter for iOS will build it - a rented Mac by the hour, a hosted CI service with macOS runners, or a friend with a MacBook and an afternoon. You still need your own Apple Developer account, because the app is published in your name.

Both stores

Keep the version name the same across both so a support conversation about "version 1.4" means one thing. The version code and Apple's build number are separate counters and do not need to agree.

Building

Turning your settings into an installable app. A few minutes, streamed live, and it carries on without you.

What a build does

It generates a complete Flutter project from your settings, then compiles it. The project is kept between builds, so the second build of an app is considerably faster than the first - the first one has to fetch the Android toolchain and every package.

The log streams as it happens. You can close the tab, and you can come back to a build in progress from another device; the build is running on the server, not in your browser.

One at a time

A second build while one is running is refused with a clear message rather than queued. Two Android builds at once on one machine mostly means both run out of memory.

APK or AAB

APKAAB
Install on a phoneYesNo
Upload to Google PlayNoYes
Use it forTesting, and sending to people directlyPublishing

APK is the default because it is what you need first. When you are ready to publish, build an AAB.

The APK is built only for the processor types real phones use, which keeps it around a third smaller than one built for everything.

Version numbers

Two of them, and they do different jobs.

  • Version name - what people see, like 1.4.0. Yours to choose.
  • Version code - a whole number Google Play uses to tell which build is newer. It must go up with every upload.

The version code is increased automatically before each build, and it clears every code you have ever built under rather than just the last one - Play rejects a reused code even if you edited the number downwards in between. That rejection arrives after both the build and the upload have been waited through, which is a slow way to learn.

Moving an existing app across

If your app is already on Play, set the version code by hand to match what is published before your first build here. A newly created app leaves a hand-set code alone until something has been built under it.

The drift warning

If you change settings after a build, the app tells you the artifact you can download is older than the settings you are looking at. It is easy to change an icon, forget to rebuild, and upload the previous file - and the resulting confusion is hard to diagnose from the store's side.

Artifacts and downloads

Each build keeps its own artifacts and its own log, so you can go back to an earlier one. Downloads are behind links that do not expose your project layout, and they need your session - artifacts are not public.

The project .zip excludes build output, caches, your keystore and the temporary signing file. That keeps it around 2 MB instead of 300 MB, and keeps signing passwords out of a Downloads folder.

When a build fails

Common failures get a plain sentence above the raw log:

What it saysWhat to do
Out of memory The machine ran out during compilation. Try again; if it keeps happening the server needs more memory or swap.
Missing keystore Upload a signing key, or check the alias matches the one in the file.
Licence not accepted An Android SDK licence has not been agreed on the server. An administrator runs sdkmanager --licenses.
Bad URL The website address is not something the app can load. Check it opens in a browser.

Anything unrecognised shows the log unchanged rather than a wrong guess. The real error is usually in the last twenty lines.

Generating without building

You can produce the project without compiling it. That is the fast way to get the iPhone project onto a Mac when you do not need an Android build, and it is also how you inspect exactly what would be compiled.
